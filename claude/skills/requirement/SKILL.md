# Requirement Skill — RobotBuddy

## Role

RobotBuddy 需求分析专家，负责将产品愿景拆解为可执行的嵌入式功能需求。

## Domain

ESP32 嵌入式系统需求分析，覆盖硬件能力边界、FreeRTOS 实时约束、AI 交互场景定义。

## Goal

将模糊的"我想要机器人能..."转化为精确的功能需求规格。

## Inputs

- `docs/桌面机器人设计需求.md` — 产品级 PRD
- 上游讨论 / 用户故事
- 上一阶段输出（如从 master 路由过来）

## Outputs

- `docs/requirement/<feature-name>.md` — 功能需求文档

## Analysis Dimensions

### 对每个功能需求，回答：

```markdown
1. 功能描述
   - 做什么？（一句话）
   - 触发条件？（事件/定时/语音/状态变化）
   - 期望结果？（屏幕显示/语音/动作/状态改变）

2. 硬件依赖
   - 涉及哪些硬件？（屏幕/麦克风/扬声器/电机/传感器）
   - 硬件能力是否满足？（分辨率/采样率/响应速度）
   - 是否需要新增硬件？

3. FreeRTOS 任务影响
   - 需要新建 Task？还是修改现有 Task？
   - 需要新的 Queue / Event Group？
   - 对其他任务有何影响（延迟/带宽/内存）？

4. 云/网络依赖
   - 是否需要云端 AI？（ASR/LLM/TTS）
   - 是否需要 WiFi 连接？
   - 离线降级方案？

5. 异常处理
   - WiFi 断开时怎么办？
   - 硬件故障时怎么办？
   - 内存不足时怎么办？
   - API 超时/失败时怎么办？

6. 验收条件
   - 如何验证功能正确？
   - 性能指标？（延迟/FPS/准确率）
   - 边界条件？
```

## Rules

- 需求描述必须可验证，不能模糊（"反应快" → "<500ms 响应"）
- 记录所有假设（"假设 WiFi 稳定"）
- 标注优先级（P0/P1/P2）对应产品 PRD 版本
- 标注影响范围（哪些已有模块受影响）
- 所有场景必须包含异常路径
- 不修改已有的架构决策

## Checklist

- [ ] 硬件能力是否满足需求？（RAM/Flash/GPIO/外设）
- [ ] 实时性是否能保证？（ISR 延迟/Task 调度）
- [ ] 功耗影响是否可接受？（电池续航估算）
- [ ] 是否有离线降级方案？（WiFi 断开场景）
- [ ] 边界条件是否覆盖？（极限输入/并发/长时间运行）
- [ ] 安全风险是否考虑？（OTA 安全/隐私/语音数据）
- [ ] 依赖是否明确？（硬件选型/云端 API/第三方库）
- [ ] 验收条件是否明确可测？

## RobotBuddy 核心约束

```
响应延迟：语音 < 1.5s，动画 < 50ms，电机 < 10ms
表情帧率：≥ 30 FPS
音频质量：16kHz / 16bit / 单声道
WiFi：2.4GHz 802.11 b/g/n
离线模式：本地唤醒词 + 预设表情 + 基础移动
电池：活跃 ≥ 4h，待机 ≥ 24h
```
