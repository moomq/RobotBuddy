# /deploy — RobotBuddy OTA 远程部署

## 用途

将已构建的 RobotBuddy 固件部署到目标设备，支持 OTA 远程升级和手动烧录两种方式。

## 适用场景

- 开发阶段快速 OTA 推送到测试设备验证改动
- 生产环境安全部署（签名验证 + 证书锁定）
- 批量多设备同步升级
- 紧急回滚到上一个稳定版本
- 出厂固件恢复（factory 分区保底）

## 工作流

```
第 1 阶段：部署前确认
├── 1.1 确认目标设备
│   ├── 设备 ID (MAC 地址 / 自定义 ID)
│   ├── 当前固件版本 → 确认是否需要升级
│   ├── 设备在线状态 → MQTT / mDNS 查询
│   ├── 电量状态 → 必须 ≥ 20%，否则拒绝部署
│   └── 输出：设备清单 + 状态确认
├── 1.2 确认固件版本
│   ├── 固件版本号 (SemVer: MAJOR.MINOR.PATCH)
│   ├── 确认已通过 /release 发布流程（tag 已打、CHANGELOG 已更新）
│   ├── 确认固件已构建: build/robotbuddy.bin
│   └── 输出：固件版本确认
├── 1.3 确认部署方式
│   ├── --ota: 通过 HTTPS OTA 推送（默认）
│   ├── --mqtt: 通过 MQTT 通知设备自助下载
│   ├── --manual: 手动串口烧录
│   ├── --batch: 批量多设备部署
│   └── 输出：部署方式确认
└── 1.4 输出：部署确认清单

第 2 阶段：固件准备
├── 2.1 版本号确认
│   ├── 读取 app_version.h: FW_VERSION 宏
│   ├── 对比目标设备当前版本 → 确定升级/降级/已是最新
│   └── 降级操作 → 要求用户手动确认（不允许自动降级）
├── 2.2 SHA256 校验和计算
│   ├── sha256sum build/robotbuddy.bin
│   └── 写入 manifest.json → {"version":"x.y.z","sha256":"...","size":...}
├── 2.3 RSA-2048 签名（生产环境必须）
│   ├── 使用发布私钥签名固件
│   └── 生成 firmware.sig 签名文件
├── 2.4 上传到 OTA 服务器
│   ├── 上传固件: firmware_vX.Y.Z.bin → OTA 服务器存储
│   ├── 上传清单: manifest.json → /ota/manifest/
│   ├── 上传签名: firmware_vX.Y.Z.sig → /ota/signatures/
│   └── 验证服务器端文件完整性（SHA256 二次校验）
└── 2.5 输出：固件就绪确认 + 服务器端 URL

第 3 阶段：执行部署
├── 3.1 OTA 推送流程 (--ota)
│   ├── 设备发现 → MQTT / mDNS 确认设备在线
│   ├── 下发 MQTT ota/command 消息:
│   │   {
│   │     "cmd": "upgrade",
│   │     "url": "https://ota.robotbuddy.local/firmware_vX.Y.Z.bin",
│   │     "version": "X.Y.Z",
│   │     "sha256": "...",
│   │     "signature_url": "https://ota.robotbuddy.local/firmware_vX.Y.Z.sig",
│   │     "level": "optional|mandatory"
│   │   }
│   ├── 设备端 ota_handle_mqtt_command() 解析并进入状态机
│   ├── 设备下载固件（HTTPS + Range 断点续传）
│   ├── 设备 RSA-2048 签名验证 + SHA256 校验
│   ├── 设备标记启动分区 + 重启
│   ├── 设备启动后 30s 健康检查
│   ├── 健康检查通过 → COMMITTED → 部署成功
│   └── 健康检查失败 → 自动回滚 → 告警通知
│
├── 3.2 MQTT 通知流程 (--mqtt)
│   ├── 仅下发 MQTT 通知，不主动推送固件
│   ├── 设备收到通知后自助决定升级时机
│   │   (如在 WiFi 质量好 / 电量充足 / 空闲时下载)
│   ├── 适用场景: 生产环境、电量敏感场景
│   └── 升级完成后设备上报结果到 MQTT
│
├── 3.3 手动烧录流程 (--manual)
│   ├── idf.py -p {PORT} flash
│   ├── 烧录完成后手动验证启动
│   ├── 适用场景: 开发调试、OTA 失效后的恢复
│   └── 注意: 手动烧录会覆盖 factory/ota_0 分区
│
├── 3.4 批量部署流程 (--batch)
│   ├── 从设备列表文件读取目标设备 ID
│   ├── 分批并发推送（默认每批 5 台）
│   ├── 逐台监控升级进度与结果
│   ├── 汇总批量部署报告
│   └── 失败设备自动重试 1 次，仍失败则记录
│
└── 3.5 输出：部署进度实时反馈

第 4 阶段：部署验证
├── 4.1 设备上线确认
│   ├── MQTT 在线状态: device/{id}/status = "online"
│   ├── 版本号上报: device/{id}/version = "X.Y.Z"
│   └── 预期上线时间: 重启后 ≤ 15s
├── 4.2 版本验证
│   ├── 对比上报版本号与目标版本号
│   ├── 确认启动分区指向正确 OTA 分区
│   └── 确认 otadata 状态为 COMMITTED
├── 4.3 功能冒烟测试
│   ├── WiFi 连接正常 (RSSI 达标)
│   ├── MQTT 连接正常
│   ├── 屏幕显示正常 (表情渲染 1 帧)
│   ├── 音频播放正常 (TTS 一句话验证)
│   ├── 传感器读取正常 (MPU6050 I2C 通信)
│   └── 预期: 所有检查项 30s 内通过
├── 4.4 部署标记
│   ├── 更新部署记录 (设备 ID + 版本 + 时间 + 结果)
│   ├── 成功: 标记为当前活跃版本
│   └── 失败: 记录失败原因，触发告警
└── 4.5 输出：部署结果报告
```

## 与 /release 的区别

| 维度 | /release | /deploy |
|------|----------|---------|
| 关注点 | 版本发布：打 tag、写 CHANGELOG、构建发布包 | 固件部署：将构建好的固件推送到设备 |
| 输入 | 开发完成的代码 | /release 产出的固件 (firmware_vX.Y.Z.bin) |
| 产出 | Git tag + CHANGELOG + Release Notes + OTA 包 | 设备上的新固件 + 部署结果报告 |
| 何时执行 | 功能开发完成后，准备发布版本时 | /release 完成后，需要将版本推送到设备时 |
| 目标 | 保证版本在代码层面可追溯 | 保证固件在设备上可靠运行 |
| 回滚 | 代码回滚 (git revert) | 固件回滚 (OTA 分区切换) |

典型流程: `/feature` → `/review` → `/release` → `/deploy`

## 部署方式选项

| 选项 | 说明 | 适用场景 |
|------|------|----------|
| `--ota` | 通过 HTTPS OTA 推送固件到设备（默认） | 日常开发验证、常规版本升级 |
| `--mqtt` | 仅通过 MQTT 通知设备有新版本，设备自助下载 | 生产环境、设备自行选择升级时机 |
| `--manual` | 手动串口烧录 (idf.py flash) | 开发调试、OTA 失效恢复、首次烧录 |
| `--batch` | 批量多设备部署，分批并发推送 | 多设备同步升级 |
| `--mandatory` | 标记为强制升级（严重安全漏洞修复） | 安全补丁、关键 Bug 修复 |
| `--dry-run` | 模拟部署，不实际执行，仅输出部署计划 | 部署前预检 |
| `--timeout <s>` | OTA 超时时间（默认 600s） | 弱网环境延长超时 |
| `--retry <n>` | 失败重试次数（默认 3 次） | 不稳定网络环境 |

## OTA 部署流程详解

```
                    ┌─────────────────────────┐
                    │   /deploy 启动            │
                    └───────────┬─────────────┘
                                │
                    ┌───────────▼─────────────┐
                    │ 1. 设备发现               │
                    │  - MQTT device/{id}/status│
                    │  - mDNS _robotbuddy._tcp │
                    │  - 检查 电量 ≥ 20%       │
                    │  - 检查 设备在线          │
                    └───────────┬─────────────┘
                                │ 在线 + 电量充足
                    ┌───────────▼─────────────┐
                    │ 2. 固件上传 OTA 服务器    │
                    │  - firmware_vX.Y.Z.bin   │
                    │  - firmware_vX.Y.Z.sig   │
                    │  - manifest.json          │
                    └───────────┬─────────────┘
                                │
                    ┌───────────▼─────────────┐
                    │ 3. MQTT 推送升级指令      │
                    │  Topic:                  │
                    │  robotbuddy/{id}/ota/cmd │
                    │  Payload:                │
                    │  { cmd, url, version,    │
                    │    sha256, sig_url,      │
                    │    level }               │
                    └───────────┬─────────────┘
                                │
                    ┌───────────▼─────────────┐
                    │ 4. 设备端 OTA 状态机      │
                    │  IDLE → CHECKING          │
                    │  → DOWNLOADING (Range)    │
                    │  → VERIFYING (RSA+SHA256) │
                    │  → READY → REBOOTING      │
                    └───────────┬─────────────┘
                                │ 重启
                    ┌───────────▼─────────────┐
                    │ 5. 设备启动 + 健康检查     │
                    │  VERIFYING_NEW (30s)      │
                    │  ├─ WiFi 连接 OK?         │
                    │  ├─ MQTT 连接 OK?         │
                    │  ├─ 显示正常?              │
                    │  ├─ 传感器正常?            │
                    │  ├─ 表情渲染 OK?           │
                    │  └─ 音箱播放 OK?           │
                    └───────┬───────┬───────────┘
                            │ OK    │ FAIL
                    ┌───────▼──┐ ┌──▼──────────┐
                    │ COMMITTED │ │ ROLLING_BACK │
                    │ 升级成功   │ │ 自动回滚     │
                    └───────────┘ └──────────────┘
```

## 回滚说明

部署的回滚逻辑由 OTA 系统自动管理，详见 `ota` skill（`.claude/skills/ota/SKILL.md`）。核心策略如下：

```
自动回滚触发条件:
├── 健康检查失败: 启动后 30s 内任一检查项未通过
├── watchdog 重启 ≥ 3 次: 新固件反复 watchdog，自动标记无效
├── panic 重启 ≥ 5 次: 新固件反复 panic，自动回滚
└── 服务器下发回滚命令: MQTT {"cmd":"rollback"}

回滚机制:
├── esp_ota_mark_app_invalid_rollback_and_reboot()
│   → 标记当前启动分区为 INVALID
│   → 自动切换到上一个 VALID 分区
│   → 如果 ota_0 和 ota_1 都 INVALID → 回退 factory
└── factory 分区永不覆盖，作为最后保底恢复手段

回滚后行为:
├── 设备通过 MQTT 上报回滚原因和版本信息
├── 部署端接收告警 → 记录失败原因
└── 根据失败原因决定是否修复后重新部署
```

## 注意事项

- **factory 分区不可 OTA 覆盖** — OTA 只能写入 ota_0 或 ota_1，factory 是最后保底恢复手段，永远保留出厂固件
- **低电量禁止 OTA** — 电量 < 20% 时拒绝执行 OTA，防止刷写过程中因断电损坏 Flash 分区
- **OTA 期间禁止断电** — 设备端在 OTA 状态机运行期间（DOWNLOADING / VERIFYING / READY），需确保供电稳定，建议同时连接 USB 供电
- **固件签名不可省略** — 生产环境部署必须启用 RSA-2048 签名验证，防止固件被篡改或中间人攻击
- **部署前必须确认 /release 已完成** — 固件必须是已通过发布流程的版本（tag 已打、CHANGELOG 已更新），不得部署未发布版本的临时构建
- **降级需用户确认** — 部署旧版本（如从 V2.0 降至 V1.0）需用户主动确认，不允许自动降级，避免引入旧版本的安全漏洞
- **批量部署分批进行** — 批量部署时默认每批 5 台，间隔 30s，避免 OTA 服务器瞬时压力过大
- **MQTT 消息 QoS** — 部署指令使用 QoS 1（至少一次送达），确保设备不会遗漏升级命令
- **网络中断容错** — 支持 HTTP Range 断点续传，下载中断后设备从中断点继续，最多重试 3 次
- **回滚信息必须上报** — 触发回滚后，设备通过 MQTT 上报回滚原因和版本信息，部署端需及时关注回滚告警
- **部署记录持久化** — 每次部署结果应记录在设备版本台账中，便于追溯每个设备的固件变更历史
- **OTA URL 有时效性** — 签名的 OTA URL 携带过期时间戳，避免长期有效的下载链接被滥用
